# 切版是正本

## 這個 repo 是什麼

11ty + SCSS + nunjucks，push master 即部署 GitHub Pages。它是前端的**切版正本**，也是與設計師共編的標竿範例。終點是零 CSS 需維護：設計師與開發者共編這份 SCSS，再由 agent 轉成 React。

- 規範正本：`GUIDELINE.md`。專案現況（檔案樹、頁面／元件清單）：`README.md`。
- 轉換配方（root，姊妹兩份）：`TAILWIND-CONVERSION.md`（→ React + Tailwind，零手寫 CSS）、`REACT-CONVERSION.md`（→ React + SCSS，scss byte-identical 照抄）。

## 方向單向：這裡定義，下游跟上

- 跨 repo 不一致時**這裡永遠是對的那一方**。不要改切版或 GUIDELINE 去配合下游；下游沒跟上是下游的同步問題。
- 下游的判準是「**只要跟這裡不一樣的就是錯**」——逐行比，不同即錯，以這裡為準。這裡用 utility／元件 class 表達的（`mt-*`、`text-*`、`.collapse-body`…）下游不可改寫成行內 style；只有這裡自己也用行內的三種（§4：`<col>` 欄寬、資料驅動的執行期尺寸、JS 切換的 display）下游才跟著行內。
- 「數值差不多就行」只適用這個 repo（見 `slicing-architecture-rules`），**不適用下游**——那一側是像素級。
- **規範正本只在這裡維護一份。** 下游不得複製 GUIDELINE：複製品必然漂移，會殘留過時的寬鬆規則。下游那邊只留一條指標——這裡是唯一真實來源，要改前端先改這裡，再照抄。
- 唯一允許的差異是**機械轉換適配**：`class`→`className`、include→元件、`url(../images/)`→`/images/`、`@use` 路徑。那是轉換，不是改設計。
- 下游同步到哪一版由下游自己記錄。**那是它的紀錄、不是我們的依據**：不因為它落後而改切版，也不把它的現況寫進這裡的任何產出物。它的 parity 守門在同步之前紅著是正確行為。

## 不引用任何其他專案（§3-2）

這個 repo 是每一顆介面的最上游定義點。一個欄位叫什麼、值域有哪幾個、界線是多少、按下去有哪幾種結果，都在這裡決定一次再往外送。

- 註解、規範、測試訊息、可見文案裡不出現：其他專案的名字、它的常數／函式／類別／測試名、資料表與欄位名、HTTP 端點、檔名與模組路徑、docstring 引述與實測數字，以及「逆向自 X」「對齊 X」「與 X 逐字相同」「以 X 現況為忠實度基準」這族背書句。**換成代稱也不行**——換代名詞不會讓依賴消失，只讓它更難查。（產品對使用者講話時說「後端」是正常用語，不在此限。）
- **保留機制、拿掉出處**：「上限 200（某某常數）」→「上限 200 字，超過會被擋下並指名是哪一欄」。界線值、枚舉成員、錯誤結果全部留著，改成「在這裡宣告一次就是正本」。拿掉出處就沒有內容的句子，本來就只是出處，刪掉。
- 要寫的是**機制**不是出處：讀的人當場驗得動的才算。重驗方式（「打這兩輪對照就看得出來」）是合法且最好的形式。
- **拆除順序：先砍執法點，再清內容**——規則與測試會把違規長回來。
- 要驗 hook 名／契約／同 key 雙語值就在**本 repo 內部**驗（markup ↔ `src/i18n/en.json` ↔ 測試），不 grep 任何其他 repo。歷史 jQuery 專案完全遺忘、不要打開——舊碼是死歷史，讀它只會把走樣的舊寫法帶回來。
- 理由不是簡潔：本專案的測試比不到別人的程式碼，這種引用一定會爛而且爛掉沒有任何一關會紅。更貴的是方向——一份規格只要以別人的實作為根據，這個 repo 就不再是定義點，而是一份注定落後的抄本。

## 缺後端資料照樣切

- 「上游沒回那個欄位／那段資料沒落庫，所以這顆鈕做了也拿不到東西」**不是不做的理由**。假想它一定會有，把版位、文案、hook class 都定出來，在元件／頁面檔頭一句話寫明它對後端的要求（欄位名、為什麼非它不可）。
- 條件動作只掛 hook class、不假造成敗。不放按了沒反應的鈕（§5）＝**兩態都要切**，不是「先不做」。
- 交辦單寫「相依某方，等它做完」時，先判斷那是不是只是資料相依；是就照做，把相依寫成註解（寫成契約，不寫成待辦，見 `writing-rules-and-handoffs`）。
- 等資料齊了才畫，等於讓「使用者其實需要看到這個」一直沒有人在畫面上主張。**切版主張需求，後端實現它。**

## 轉換規則書是主產出

- 做範例元件的目的是**提煉可複用的律**。每做一個先問「這提煉出哪條律」，寫進 `REACT-CONVERSION.md`／`TAILWIND-CONVERSION.md`，再驗證。
- 回報以「新增／驗證了哪幾條規則」為主，元件是佐證。把重心放在「讓某個下游元件過關」就是把手段當目的。
- 檔名慣例：`<TARGET>-CONVERSION.md`，大寫，放本 repo root。

## 下游元件整份重寫，絕不 patch

- 每個元件**從切版整份重寫**：markup 逐字對照切版 html、scss 整份照抄 byte-identical、vanilla js 行為機械轉寫成 hooks。下游現況當要丟棄的廢版，不 diff／不 patch、不假設「現況大致對、只改幾處」。
- 現況每個檔都可能殘留走樣（舊 token、舊斷點、缺 wrapper、裸色、缺 aria）。patch 式改法只動被點名的幾處，其餘走樣原封不動繼承下來，而視覺指紋不一定抓得到（見 `verification-that-can-fail`）。
- 寫 task brief / dispatch 時，元件一律講「從切版 `X.html` + `X.js` 整份重寫出這個元件」，**不要列「刪現況的 A、加 B」這種 patch 動作清單**。把這條寫進 plan 的 Global Constraints，讓每個 task/reviewer 都吃得到。
- 現況只拿來對**一件事**：consumer 介面（props 被哪些頁面用、要向後相容）。實作零參考現況。
- 唯一從現況保留的是**切版沒有、屬應用層**的邏輯（權限過濾、fetch、路由、框架慣例）——那不是走樣、是真實需求。

## 交付

直接在 master 上 commit 並 `git push origin master`。不開 feature branch、不開 PR（push 觸發 Pages 部署）。
