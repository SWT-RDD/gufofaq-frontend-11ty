# 完成的定義

## 取捨依據是品質，不是成本

**前提：這是切版標竿專案，產出是給人照著做的範本——沒有線上使用者、沒有外部消費者、沒有相容性包袱。** 所以這裡的取捨依據只有一個：最終架構與成果的品質。「比較省時間」「比較省成本」不構成理由。

- **不要抽樣、不要縮水**：該逐檔讀就逐檔讀、該派滿扇出就派滿、該一輪接一輪跑到零發現就跑（見 `carpet-audit`）。工作量大不是縮減的理由。
- **交完整版，不要開「快速版 vs 完整版」的選單。** 範圍已經清楚時就一路做完，不必逐段徵詢。
- **repo 內部的替換做乾淨的一次**：不留遷移期、不加漸進切換的 flag、不讓新舊路徑並存。這條的前提是上面那句「沒有外部消費者」——有消費者的介面不適用。
- **不 patch 現況求快**：該整份重寫就整份重寫；為了更乾淨的架構做大規模重構是值得的。
- 適用範圍是程式碼與架構決策。**不可逆的動作**（刪除非本專案資料、覆寫他人未提交的工作、對外發送）不在此列，一律先確認。

## 完成的判準

- **整件做完**才算數，不是做一部分就回報。**有小尾巴＝沒完成**，不要拿零星未完成項來問「這尾巴怎麼處理」。
- 做完後**地毯式掃描整個專案**確認沒有任何沒處理的地方（grep／程式化掃描／瀏覽器實測）。
- **任何保留不處理的，都要有明確理由**（假資料／示範內容／API 佔位）。
- **掃到乾淨、確認完成，才回報或問使用者。** 不要中途拿一串待辦來問。
- i18n 的具體標準：切英文時 **UI 零繁中**，只有假資料／示範內容可留繁中（清單見 `slicing-architecture-rules`）。

## 回報前自問

- **逐項對照「宣稱驗過的」與「真的跑完的」**：每一塊是否真的有人或有 agent 完整跑完並回報？中止或崩掉的那一塊要明列覆蓋到什麼程度，不併進「已驗證」。誠實列出部分覆蓋，勝過宣稱已經收斂。
- **「綠」的證據是看到 pass 的數字**，不是沒看到 fail（見 `verification-that-can-fail`）。
- 回報單／交辦單直接輸出成聊天文字讓人複製，內容要自足到「對方照這張單就能接手」（見 `writing-rules-and-handoffs`）。
