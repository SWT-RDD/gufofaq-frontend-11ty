# 完成的定義

## 資源無限，只求最好的成果

- **不省 token、不省時間、不考慮生產使用者、不考慮破壞性重構的後果。** 這是切版標竿專案，沒有真實線上使用者、沒有相容性包袱；唯一的評分標準是最終架構與成果的品質。任何「省成本／省時間／怕破壞」的折衷都只會降低品質，是純損失。
- **不要抽樣、不要縮水**：該逐檔讀就逐檔讀、該派滿扇出就派滿、該一輪接一輪跑到零發現就跑（見 `carpet-audit`）。「這樣很花 token／很久」永遠不是縮減理由。
- **不要提出「快速版 vs 完整版」二選一，也不要問「要不要繼續」。** 直接做完整版、直接繼續。
- **不做向後相容、不留遷移期、不加 feature flag 漸進切換、不留舊路徑並存。** 要換就整份換掉，舊的直接刪。
- **不 patch 現況求快**：該整份重寫就整份重寫；為了更乾淨的架構做大規模重構永遠值得。
- 適用範圍是程式碼與架構決策；**不**把「不必確認」延伸到刪除非本專案資料、覆寫他人工作這類不可逆操作。

## 完成的判準

- **整件做完**才算數，不是做一部分就回報。**有小尾巴＝沒完成**，不要拿零星未完成項來問「這尾巴怎麼處理」。
- 做完後**地毯式掃描整個專案**確認沒有任何沒處理的地方（grep／程式化掃描／瀏覽器實測）。
- **任何保留不處理的，都要有明確理由**（假資料／示範內容／API 佔位）。
- **掃到乾淨、確認完成，才回報或問使用者。** 不要中途拿一串待辦來問。
- i18n 的具體標準：切英文時 **UI 零繁中**，只有假資料／示範內容可留繁中（清單見 `slicing-architecture-rules`）。

## 回報前自問

- **我宣稱驗過的每一塊，是真的有 agent／我跑完，還是崩掉之後腦補的？** 誠實報告勝過灌水收斂——只有部分覆蓋就明講哪塊、覆蓋到什麼程度。
- **「綠」的證據是看到 pass 的數字**，不是沒看到 fail（見 `verification-that-can-fail`）。
- 回報單／交辦單直接輸出成聊天文字讓人複製，內容要自足到「對方照這張單就能接手」（見 `writing-rules-and-handoffs`）。
