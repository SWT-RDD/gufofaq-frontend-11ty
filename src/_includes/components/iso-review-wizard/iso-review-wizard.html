{# ── type-to-confirm 片語──────────────────────────────────────── **片語是「值」，不是 chrome，所以它永遠不掛 `data-i18n`。** label 與 placeholder 若各掛一顆 key（繁中要打「刪除」、英文要打 `DELETE`），就是**同一道閘在兩個語系要求不同的輸入**， 而 React 端比對的只會是其中一份，另一個語系的使用者照著畫面打就是解不開。 站內正典：manage-tenant-modal 的 type-to-confirm 打的是**租戶名稱**（一個值，兩個語系 都打同一串）。故一律是語言中立的固定字串， label 走「前綴 key ＋片語節點＋後綴 key」（§4-2 前後綴 key 自帶分隔空白）。 **片語還要跟著上一步選的動作換一組**：三個動作 purge／delete／freeze， idle 態三顆動作鈕各對一個。 **三顆不可以共用同一串**：共用的話，選了「凍結逾時帳號」的人會被要求打「刪除」。 三組片語由 `data-phrase-<動作>` 承載，React 依選定的動作把可見那一顆換上去。 **刻意不用 `data-text-<態>`／`data-key-<態>` 那組資料槽**：那一族的定義是「繁中原文 ＋ 對應的 i18n key」，而這裡的重點正是**這串字不翻**，掛上去會讓下一個人以為少了一半。 #}
{# 前綴的繁中是「請逐字輸入」而不是「請輸入」：後者與 `common.pleaseEnter` 逐字相同， §4-2「繁中原文相同的 chrome 沿用既有 key」會把兩顆判成同文異 key，而那顆是 placeholder 專用、不帶尾空白，這裡沿用它反而會讓英文黏成 "Please enter DELETE-ACCOUNT"。 #}
{# placeholder 與 label 那顆片語節點是**同一組三態**：只給 label 三態槽、placeholder 寫死一個 的話，選「凍結逾時帳號」時欄位裡仍會提示 DELETE-ACCOUNT——那是同一個 bug 的另一半。 不掛 data-i18n-placeholder：片語是值、不隨語言變（§4-2 type-to-confirm）。 #} 片語要逐字相同（含大小寫與連字號），而且會隨上面選的動作換一組；它不隨語言變。
{# 送出處置是整台唯一的寫入，所以標 admin 的是**這一顆**。低於該級時動作鈕不渲染（§5） ——標反了的話，稽核員反而看得到一顆「確認執行（不可逆）」，按了必定被拒。 「取消」是純前端互動（回 idle 態），不標。 #} {# 「（不可逆）」**只對三顆動作裡的兩顆成立**：「刪除逾時資料」與「刪除逾時帳號」沒有回頭路， 而「凍結」有對稱的解凍（解凍時把凍結那段時長補回到期日，剩餘天數原封保留）， 對它說不可逆是假的警語——假警語會讓真的那兩顆一起被當成裝飾。 故做成隨動作切換的兩態（§4-2 `data-text-<態>`＋`data-key-<態>`：這一句是 chrome、要翻， 所以繁中原文與 key 都要給，與上面那顆「片語」剛好相反）。靜態稿演的是不可逆那一態。 #} {# 第三態 `busy`＝**送出中**（處置請求在途）。它與上面兩態不同軸： 前兩態由「選定的動作」決定，`busy` 在請求在途時**蓋過**那兩態，所以這一格的字在任一 時刻仍然只會是三者之一，槽照樣掛在同一顆元素上（React 讀槽、不自己拼字串）。 為什麼一定要有這一顆：切版是靜態原型，畫得出「確認執行」畫不出「處理中…」， 於是這句繁中在切版沒有家，React 只好就地多一顆 key ——那等於在 React 端開了第二個 文案正本，而字典比對、孤兒 key、fpdiff 三張網一張都看不到（REACT-CONVERSION §③ 「送出中／載入中」那一族：回切版給它一個渲染點，`REACT_ONLY` 只是過渡登記）。 這一顆的家選在**這顆鈕**而不是元件庫頁：§③ 的判準是「會換字的那一格用兩態槽」， 而這正是那一格。 **busy 那一態的 `disabled` 不進 markup**：這一稿演的不是「送出中」，靜態稿沒有那一刻。 （鈕上確實有一顆 `disabled`，但它是另一件事——見下一段的 type-to-confirm 鎖。 REACT-CONVERSION §⑥ 列的兩種合規 disable：進行中、以及窗內看得見的解鎖條件未滿足。） #} {# 這是整台精靈**唯一的寫入鈕**，所以 `data-toast` 一段都不能少 ⇒ 少了會同時出兩件事： ①它整顆掉出 §4 閘門測試的母體（那條測試以「`data-toast-type` 含 success」為母體）； ②`toast.reviewApplied` 這顆 key 在切版就不存在，而消費端照樣要把那幾段字讀出來 ——於是長出一顆切版從未定過的文案 key，正是本檔上方那段警告的情況（§5：文案正本在切版）。 分支對回這一步的實際出口：它**逐租戶各自成敗**（整批不回捲、不中途拋掉剩下的）， 所以「部分租戶失敗」是一條真實可達、而且與 「整批送不出去」要做的事完全不同的結果。「權限不足」不列——那一級 走「動作鈕不渲染」（§5 渲染規則）。 ⚠️ **這一顆是三段**：error 在第三段，第二段是「部分租戶失敗」。假設「末段即 error」 的消費端會在這裡接錯位（`|` 分段是索引契約）。 #} {# **`disabled`＝type-to-confirm 尚未解鎖**（同 manage-tenant-modal 危險操作區那兩顆）： 這一稿演的是片語欄空著的那一刻，而片語欄的全部意義就是「沒逐字打對之前按不下去」。 它不是把 `data-toast` 的任何一段演掉——那三段是這顆鈕**送得出去之後**的結果集合 （送出成功／部分租戶失敗／整批送不出去），與「現在還不能按」不同軸；解鎖條件本身 常駐可見（上面那顆 `reviewConfirmHint`，`aria-describedby` 接著），使用者看得到自己 差什麼，所以不需要也不該改成 warning toast（REACT-CONVERSION §⑥ 的第二種合規 disable）。 #}
