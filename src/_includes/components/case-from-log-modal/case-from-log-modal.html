{# 從問答紀錄一鍵建案例（2-2-4 批次回歸）。切版這一份就是它的正本。 為什麼它是主要入口而不是「進階功能」：人不會另外坐下來寫回歸案例，是「這一則答錯了」 才想把它留成案例。所以**斷言是自動推導出來的**，這扇窗不提供「先建再補」——一則沒有斷言 （或只有主觀分）的案例永遠通過，在基準比較裡永遠落在「無變化」。 觸發鈕是 2-2-4 的 `.js-case-from-log`：開窗前要先選定「加到哪一個案例集」＝業務條件開窗， 故不掛 data-open-modal（GUIDELINE §5）；元件庫展示頁另有示範觸發器。 **閘門宣告的家在這裡、不在那顆觸發鈕上**（§4：真正送 API 的是窗內那顆確認鈕，觸發鈕只負責 「先選定要動哪一筆」）。下方確認鈕的 `data-capability="settings:write history"` **兩顆並列＝AND**： 建案例這件事要的是設定的寫入能力，而它同時會去讀提問、答案與來源文件名，故另要一次 「問答紀錄」能力——少了那一道，只有設定權限的人可以拿任何一個問答紀錄編號從側門把該租戶的 問答讀出來（那些字會原樣變成案例的問題、前置對話與斷言）。 2-2-4 那顆觸發鈕因此**不掛**這組屬性：掛了就是同一道閘門在同頁被宣告兩次。同頁另兩顆條件開窗鈕 （刪除案例集／刪除案例）也都只宣告在 delete-modal 的確認鈕上——三顆一致。 確認鈕**刻意不掛 btn-close-modals**：它的 toast 有一段「這一筆推導不出期望，換一筆」， 那正是留在窗內就能修正的驗證結果（GUIDELINE §5：含可就地修正的 warning 分支者不自動關窗）。 兩種拒絕在文案上必須分得開： **這一筆紀錄不適合**（沒有答案、被政策擋下、前置對話超過上限、前置鏈結中間那一輪 已不存在）——換一筆問答，或改用手動建立。 **系統有問題**，三種（可見文案要三種都列得出來，少一種就是那一態的使用者讀到一句 對不上自己畫面的話）：命中清單形狀不符、 第一筆命中沒有文件身分（既沒有文件 id 也沒有檔名）、 前置鏈結指到別租戶的紀錄（聊天室屬單一租戶，那是資料本身不一致） ——不是使用者的操作問題，要回報。 混成一句「建立失敗」的話，使用者只會一直換紀錄重試一個修不好的東西。 結果區是 role="status" live region 且**常駐**（GUIDELINE §4：內容到達前節點就要在 DOM 裡， 條件渲染等於報讀器永遠不播報）。示範內容刻意演「勾了帶入前置對話卻拿到 0 輪」那一態， 而**那一態的理由很容易寫錯**：不是「問答時沒把聊天室帶下去」——問一題一定帶著聊天室的 對外參照走，帶得很清楚；不收的是**呼叫端直接給的內部聊天室整數** （那是全域遞增的號碼，跨租戶猜得到），對外只認那顆參照。 真正會拿到 0 輪的是「這一筆紀錄本身就沒有前置」（單題成室、或那顆參照解不出來）。 那一態必須被講出來，否則使用者只會以為前置對話帶進去了——這句話是使用者讀得到的紅字， 理由寫錯比不寫更貴（§3-2）。 「推導理由」與前置對話那句提示是執行期算出來的整句話（資料，不翻）； 「自動帶出的斷言」是型別識別字（`cites_document` 這種業務識別字，不翻）。 #}
