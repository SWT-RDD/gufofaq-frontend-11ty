{# 重設密碼 modal，取自 5-5-1_userManagement 頁「重設密碼」鈕（.js-reset-password）：管理者代替指定成員重設密碼。 開窗需先選定哪一位成員才知道重設誰＝業務條件開窗，故該鈕保留真 app hook class、不掛 data-open-modal（GUIDELINE §5）； 彈窗本體回歸切版：新密碼＋確認新密碼，欄位寫法比照 5-1-1_accountInfo「變更密碼」區塊 （label.required + placeholder），差別是管理者代為重設、不需輸入舊密碼。 驗證結果走確認鈕的 toast warning 段，不做逐欄內嵌訊息（GUIDELINE §4：全站一種回報方式）。 確認鈕的 data-toast **由使用頁提供**（resetToast / resetToastKey / resetToastType）——這顆彈窗被兩頁共用， 而兩條路徑的守衛集合不同：5-5-1 走 `POST /users/{id}/reset-password`，`users.py` 呼叫 `_assert_tenant_manageable(u)`（403「平台角色持有者不可由租戶管理者管理」）；5-6-1 走 `POST /platform/users/{id}/reset-password`，`platform.py` **只有一條 404**。 共用一組四段的話，平台管理員站在平台管理端會被告知「請由平台管理端處理」—— §5：列出不可能的結果與只演成功一樣是說謊。未給參數時退回最小的成敗兩段。 「兩次不一致」是可就地修正的驗證 warning，故確認鈕**不掛 btn-close-modals**（§5：每點必關窗會打斷修正、演不出該態； 只有純成敗或不可就地修正的 warning 才掛）；成功後的關窗交業務 js，取消鈕／X 仍可關。鈕緊鄰 #resetNewPasswordInput／ #resetConfirmPasswordInput 兩欄位 id＝可定址契約，React 由此綁定、免自創 hook（§5）。 （除了上面那三個 toast 參數之外無其他參數。） #}
