{# 執行流程（後台測試區詳細觀測）：把「這次回答執行到哪一步、 現在在哪個 node、用了哪些工具、可回答性判定、agent 推理」畫成一張類 mermaid 的直式流程圖， 並在頂端給整體執行摘要（token/延遲/TTFT/檢索筆數/模型）。**步驟列與工具軌跡收在同一個元件**：攤成兩張表的話，讀的人沒辦法把「第幾步」與「那一步用了什麼工具」對起來。 正典管線各節點依序畫出（未跑到＝待處理），由每一步自己回報的狀態點亮（只吃 completed）； 當前節點高亮＝最後一個 completed 的下一個正典節點。狀態 class：is-completed（--success 綠點）/ is-running（--brand-ink 深墨點，當前高亮）/ is-skipped（--text-muted 灰虛，分支/反問跳過）/ is-failed（--danger）/ 其餘 pending（--border）。 收合機制復用 ui/accordion（根 .js-accordion + 每節點列的 .accordion-btn + 隱藏的 .detail-row > .accordion-content，見 ui/accordion accordion.js：GufoSlide 300ms、aria-expanded 每路徑同步）—— 本元件不自帶 js；表格結構是 accordion findContent（closest("tr")+.detail-row 兄弟列）的硬需求。 每節點（摘要列＋隱藏詳細列）以 {% for %} 內嵌渲染（GUIDELINE §9 陷阱：元件內部的 for 不可再巢狀 include 子元件，會靜默渲染成空白）。真值由 React 端的串流事件驅動；此處為靜態示範。 巢狀（skill）：租戶自訂 skill 被 agent 呼叫時會跑一個 scoped 子 agent 迴圈，其子步驟以 parent 鏈 掛成子樹。 **`depth` 是「顯示用的樹深」，不是 skill 的遞迴層數**——那個同名的數字裡，一個 skill 呼叫與它自己的子步驟同值；縮排要的是 parent 鏈的層數，故 1＝被正典節點呼叫的 skill、2＝它的子步驟、 3＝再一層。**值域夾在 3**（scss 只定義到 `is-depth-3`）——插值出 `is-depth-4` 這種未定義的 class 只會靜默不縮排，所以夾在模板裡而不是靠資料自律。 skill 節點另有 skill/version/iterations/error 明細列——資料裡有的就要看得見； 刻意**不**收工具參數與結果原文（那是洩漏面，見下方 `params` 那一段）。 **時間的取整規則（全站唯一一份，在這裡宣告一次就是正本，使用頁不要各自另發明）**：時間欄與 摘要的三個時間值一律照這一條寫——**≥1s 是一位小數、四捨五入** （4,096ms → 4.1s、3,340ms → 3.3s、1,784ms → 1.8s、2,140ms → 2.1s），**<1s 是整數毫秒**。 `1.95s` 這種兩位小數是這條規則產不出來的形狀。示範資料的摘要要能從節點推導（§6）：**延遲**＝已跑過 節點的耗時和、**TTFT**＝答案節點（`respond_generate`／`respond_no_answer`）的起點＝它之前那幾站 的和；兩個都先加成毫秒、再套同一條規則取整，寫進使用頁註解時要把式子與母體一起寫出來。 **時間欄的來源**：耗時是**逐步量**的（由發射端自己量），failed 那一顆照樣有。 同一個 `step_id` 在一輪裡可能出現不只一次（agent↔tools 每來回一輪就再發一次），所以 **同一個 `step_id` 的耗時要加總、而且不做狀態過濾**——只取最後一輪等於把前面幾輪的時間抹掉。 ⇒ 每一列都印得出來，與這裡每一列都給時間對得上。 QA 直答判定（S6）：**每一輪都有一筆**判定，未命中那半也有，故節點另收五個鍵 （這幾顆值在這裡定義一次就是正本，不另發明同義詞）： decision —— `hit`／`no_exact_and_judge_rejected`／`below_score_floor`／`reconstruct_failed`／ `not_attempted` 五顆。查表查不到的值**原樣輸出**（日後多一種結論時，畫面要看得到那個生字）。 entry —— `pre_graph`（建圖前閘門）／`agent_tool`（agent 工具）：哪一道閘門做的判定。 值域就是這兩顆；同 decision，**查表查不到的值原樣輸出**。 matchedRank ＋ poolSize —— 命中在候選池第幾名／候選池筆數，**一列成對顯示**（同 score／floor 的理由：只給名次看不出池子多深、只給池子大小看不出這一筆排在哪）。未命中時 matchedRank 為空 ⇒ 只畫池子大小；poolSize 為 1 要照實顯示（agent 工具那一道本來就只判 agent 挑的那一筆）。 reusedFrom —— 這個結論是重用前一道的。掛在徽章旁當小標、**不做成第六種徽章**：它修飾的是 「結論怎麼來的」，而重用可能重用命中、也可能重用判否，一個值講不清楚是哪一種。 **同一輪出現兩個 qa_direct 節點是正常的**（建圖前判否 → agent 又判一次），逐筆依序畫、不去重。 可回答性判定與合規閘（verdict／reason／blockedRules）：三顆鍵、三個閉合值域，**都不得夾自由文字** （規則名有自己的一顆鍵 `blockedRules`，正是為了讓 `verdict` 保持閉合， 否則消費端只能做字串前綴解析）： verdict —— `generate`（素材足以回答）／`no_answer`（素材不足以回答）／`blocked`（被規則擋下） 三顆（在這裡宣告一次，就是正本）。前兩顆掛在**可回答性判定**那一站； `blocked` 只掛在**合規閘**（`input_gate`／`output_gate`）而且**只在真的被擋那一輪**—— 放行與未啟用的閘一顆 verdict 都不帶。同 decision，**查表查不到的值原樣輸出**。 比對寫成**逐字相等**是安全的：這一欄永遠是裸的那三顆，規則名不會被接在後面。 reason —— 這個判定**是從哪一層出來的**，值域是這五顆（在這裡宣告一次，就是正本）： `gate_off`（閘關著、透明直通）／`empty_material`（素材為空）／`score_floor`（分數粗篩判否， 零 LLM 的終局拒答）／`llm`（判定器實際跑了）／`judge_failed`（判定器故障 ⇒ fail-open 放行， **本輪閘門沒有生效**）。**只掛在可回答性判定那一站**——合規閘的成因走 `verdict`， 那一站沒有這顆鍵。 **值得一列的理由**：`no_answer` 那一輪只看 verdict 分不出「知識庫裡真的沒有」（`empty_material`）、 「有但都不夠像」（`score_floor`）、還是「判定器掛了所以其實沒判」（`judge_failed`）——三者要 使用者做的事完全不同（去補資料／去調門檻／去看模型設定）。`judge_failed` 尤其不能藏。 ⚠️ **這一顆與 state 綁死，別畫出組不出來的配對**（配對規則在這裡宣告一次，就是正本）： `judge_failed` ⇒ 那一站是 `failed`； `gate_off` ⇒ `skipped`（而 skipped 沒有耗時 ⇒ 時間欄留白）；其餘 ⇒ `completed`。 **`gate_off` 只有 agent 模式產得出來、`null` 只有傳統模式產得出來**，兩者都只落在 skipped 上； 反過來配（傳統的 `gate_off`、agent 主管線的 `null`）是永遠不亮的路，不畫。 blockedRules —— 被哪幾條**具名**規則擋下，`verdict == "blocked"` 時**結構保證這顆鍵一定在**。 **三態、三種畫法，空陣列與鍵不存在不可收成同一種**：有名字 ⇒ 列出來；`[]` ⇒ 仍要說「被擋」 但沒有具名規則可列（例如主題判定擋的）；鍵不存在 ⇒ 整列不渲染。 故**以字串陣列傳入**（不是頓號串好的一段字）：串成字串的話 `[]` 會塌成空字串， 與「鍵不存在」在真值判斷下再也分不開。`[]` 在 nunjucks 與 JSX 都是真值，兩邊同形。 ⚠️ **可得性與別的欄位不同**：即時串流（測試區問一題、前台問答）**一定沒有**——規則名是租戶 自取的字，而同一條串流也服務完全匿名的前台問答，跨不了那道匿名邊界； 只有事後重播那一輪的軌跡（稽核路徑，留得比串流多）才有。 ⇒ **給得出這一列的使用頁＝在演一筆重播的落庫紀錄**，與 `model` 同一條判準。 ⚠️ 也因此**不可以**把「verdict 是 blocked、卻沒有 blockedRules」畫成一句「規則名被遮掉了」： 那在即時串流上是**常態**（整顆鍵不給）；而重播那條路上它另有一個成因——租戶自己的 詞過濾命中規則名時，**整顆鍵會被丟掉**（不是抽掉那一筆，留下一份會誤導人的名單）。 同一個缺席、兩種成因、消費端分不出來 ⇒ 只能不畫。 **節點示範資料的三條形狀規則**（§6：演的必須是真的做得出來的狀態）。三處同源——本檔的內建示範 ＋每一份使用頁的 `stepFlowNodes`——改一處就要一起改： ① **`params` 只印得出形狀、印不出值。** 工具呼叫的引數**原文一律不送到瀏覽器**， 送的是它的形狀：只有**鍵名 ＋ 值的 JSON 型別名**，值、字串長度、陣列筆數一律不出，且不遞迴巢狀。 **後台測試區沒有「內部所以給原文」那條路**——同一條剝除走在每一個入口上。 畫面字串的形狀是 `[已列出/實際帶了] 鍵: 型別, 鍵: 型別`（那兩個數字的差是截斷唯一的出口，且兩個都來自 同一筆資料、不另抄一個上限）⇒ 示範值一律寫成 `[1/1] query: string` 這種形狀。 `{ query: '新住民 結婚 應備文件' }` 是這條路**結構上**送不出來的東西。 ② **`floor` 是純數字。** 門檻值就是一個數（或沒有）， 沒有單位、沒有尺標註記。`3（llm_reranker 的 1–5 尺）` 是替一個不存在的欄位編字面； 「這是哪一把尺」要讓人知道的話，那件事**已經有家了**——`ui/score-scale-note`（5-2 對話設定頁 的分數尺說明，逐字「llm_reranker：1–5（分數越高越相關）」），不是塞進這一格的值裡。 ③′ **`MCP 工具載入` 不是正典管線的一站**：工具載入失敗時才多冒出這一個節點 （狀態恆為 failed ＋ 一份載入失敗的 server 清單，顯示名自帶）。 於是它有三個推論，缺一就畫錯： ・**只在失敗那一輪出現**：正常輪次完全沒有這個節點，不是「completed 的那一站」。 ・**不算進進度分母**：`X / N` 只數正典管線節點（見下方那條），把一個只在故障時 出現的節點算進去，會讓正常那一輪的進度永遠差一格。它與巢狀子步驟同一個理由， 但機制不同——子步驟靠 `depth` 排除，這一顆靠 `offPipeline`。 ・**位置在 `Agent 推理` 之前**：工具是先載入才進迴圈的；畫在後面會讓人以為是 迴圈跑完才發現載不到。 狀態恆為 `failed` ⇒ 走既有的紅色樣式，不必新增任何 class。 ③ **節點 `label` 是這裡宣告的正典名**——`qa_direct` 那一站叫 **「QA 直答比對」**， 不是縮寫的「QA 直答」。React 端的顯示名是以 `step_id` 查一份字典， 字面分岔時畫面不會報錯，只會兩邊各說各話。 參數：stepFlowInstance（**必填**）＝同頁多實例的消歧鍵（2-2-3 一頁 include 兩次、元件庫頁三次）。 每一列的可及名稱要帶「哪一站」，那些 id 都以它為前綴；沒有它的話同頁十顆展開鈕全叫「展開表格」， 而且 id 會直接撞（§4）。正典見 components/priority-table 的 priorityTableInstance。 參數：stepFlowOwnerId（選填）＝**同頁另一份執行流程**時，指向「這一份是誰的」那個既有標題節點的 id。 instance 只解決 id 相撞，解決不了**可及名稱**相撞：2-2-3 兩側跑的是同一條正典管線，兩邊的 「序號 1 QA 直答比對 展開表格」逐字相同（§4：可見字面可以重複、可及名稱不行）。給了它， 兩側的每一顆列控制項就從「設定 A · …」起頭。同頁只有一份時不必給。 **列序號是可及名稱的一部分**：節點標籤本身會重複（agent 迴圈可以連呼同一顆工具兩次，3-4 的試跑 沙盒就演到了；元件庫的判定目錄更是十列同名），所以每一列的辨識欄前面掛一段 .sr-only 的 「序號 N」。它不可見、不動版面，但讓「第幾站」進得了無障礙樹。 參數：stepFlowNodes（選填，[{ label, state, time, depth, skill, version, iterations, error, tools, params, result, verdict, reason, blockedRules, thinking, failedServers, offPipeline, hits, score, decidedBy, floor, decision, entry, matchedRank, poolSize, reusedFrom }]） ——**值域含 0 的欄一律以「字串」傳入**（`poolSize: "0"`、`score: "0"`、`matchedRank: "1"`、 `iterations: "0"`）：這些欄的渲染條件是 `{% if node.X %}` 真值判斷，而 nunjucks 把數字 `0` 判成 false ⇒
