**逐項清單那一支排的是 `(check_type, id)`**：命中次數住在上游的問答紀錄裡、排不進 SQL， 而清單是分頁的，在一頁之內排等於假排序（第 2 頁的高命中筆數永遠上不了第 1 頁）。 兩張表照什麼排各自在畫面上講明；不講的話沒有人分得出來。 ② **消音之後又冒出來，畫面要答得出「為什麼」**。product 只在 `evidence_digest` 或 `severity` 變了才重新開啟（`_premise_changes`），並把「原判定的前提已改變（…）。處置當時的證據：…」 寫進 `note`（`_reopen_note`；這一次掃描的證據馬上要覆蓋掉舊的，`note` 是它唯一留得住的 地方）。判準是 API 給得出來的：`status` 是 `open` 而 `resolved_at` 還在 ⇒ 這一筆被處置過 又回到未處置（前提改變重新開啟，或被 `/undo` 退回；兩者都刻意留著 `resolved_by`／ `resolved_at`）。少了這一格，清單每天跳同樣的既有發現，人看兩次就不看了。 ③ **六支處置是具體的資料操作，不是「標記已讀」**。`dismiss` 是唯一不動資料的一支（product 那支逐字寫著「只動發現這一列，一個字都不碰資料」）；`disable` 寫哨兵有效期、`merge` 改 保留者的內容、`supersede` 寫外部主鍵、`add-phrasing` 新增一列。**檢查本身不改資料** （八項檢查連寫記錄的路都組不出來），這句話要在按下重新檢查之前就看得到。 `disable`／`supersede` 在租戶還沒宣告對應角色維度時會 400 並指名缺的前提 （`_require_valid_until_slot`／`_require_superseded_by_slot`），故兩支的說明與 toast 分支都講得出那個前提。 ④ **`/undo` 不是永遠成功**。判準是「我們寫出去的那一份還在不在」（稽核裡的 `content_after` 與現況逐字比對），不是「試著算出反向操作」。合併把問法併進內容開頭那一行，而再併一次是 一份文件、沒有欄位槽）與讀不開的檔逐檔列進 `ScanOut.uncovered`，各帶 `reason` 與 `detail`。 漏報比誤報嚴重，而「以為乾淨、其實沒掃」的唯一解藥是讓沒掃到的部分出現在使用者眼前。 ⑥ **任何上限／截斷都在消費點外顯**：清單的 `total`／`page`／`size`（分頁）、總覽每組只附 `top_n` 筆（不是分頁，要逐筆看走清單）、命中窗
