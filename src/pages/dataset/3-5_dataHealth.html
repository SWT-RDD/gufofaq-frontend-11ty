**排序依影響、不依發現數量**。總覽把每一組「涉及記錄的命中次數總和」算出來排序 （命中總和遞減 → 未處置數遞減 → 檢查項目字典序），因為一筆從沒被命中過的重複遠不如 一筆每天被命中 50 次的過期答案重要。命中數取的是**剝掉批次回歸重放之後**的問答紀錄 ——另抄一份取回邏輯的話，跑一次回歸就會把被重放的那幾筆推上頂端，而畫面上看起來就是 「這幾筆最常被問」。 **逐項清單排的是「檢查項目 → 發現編號」**：命中次數住在問答紀錄裡、排不進資料庫的排序， 而清單是分頁的，在一頁之內排等於假排序（第 2 頁的高命中筆數永遠上不了第 1 頁）。 兩張表照什麼排各自在畫面上講明；不講的話沒有人分得出來。 ② **消音之後又冒出來，畫面要答得出「為什麼」**。只有證據摘要或嚴重度變了才會重新開啟， 並把「原判定的前提已改變（…）。處置當時的證據：…」寫進 `note`（這一次掃描的證據馬上 要覆蓋掉舊的，`note` 是它唯一留得住的地方）。判準畫得出來：`status` 是 `open` 而 `resolved_at` 還在 ⇒ 這一筆被處置過又回到未處置（前提改變重新開啟，或被還原退回； 兩者都刻意留著 `resolved_by`／`resolved_at`）。少了這一格，清單每天跳同樣的既有發現， 人看兩次就不看了。 ③ **五支處置裡有四支是具體的資料操作，不是「標記已讀」**。「判定為非問題」是唯一不動資料 的一支（只動發現這一列，一個字都不碰資料）；停用寫哨兵有效期、合併改保留者的內容、 指定現行版寫外部主鍵、補寫問法新增一列。**檢查本身不改資料**（檢查那一側連寫記錄的路 都組不出來），這句話要在按下重新檢查之前就看得到。 停用／指定現行版在租戶還沒宣告對應角色維度時會被擋下並指名缺的前提，故兩支的說明與 toast 分支都講得出那個前提。 ④ **還原不是永遠成功**。判準是「我們寫出去的那一份還在不在」（稽核留下的處置後內容與現況 逐字比對），不是「試著算出反向操作」。合併把問法併進內容開頭那一行，而再併一次是就地 擴充同一行——同一筆保留者被第二個發現又併過之後，那一行同時裝著兩次的問法，把舊內容 寫回去會連第二次的一起抹掉，只拿掉這一次的又會留下一個誰都沒寫過的中間狀態。兩個都不是 反向操作，所以擋下來並指名。兩種擋法的文案不同，兩條都列在還原鈕的 toast 分支裡。 ⑤ **「沒掃到」是誠實記錄，不得被藏起來**。掃不到的檔逐檔列出來，各帶原因與說明。五種原因： 不是逐列匯入、也沒有逐列的擷取連結；沒有落地檔名／擷取連結的舊列；本機沒有擷取器的格式 （圖片、舊版 .doc 等）；列還在、磁碟上那一份不見了；擷取器讀不出來。漏報比誤報嚴重， 而「以為乾淨、其實沒掃」的唯一解藥是讓沒掃到的部分出現在使用者眼前。**那張表自己也有 筆數上限**，所以「總共幾個」與「逐原因幾個」（不受截斷影響）兩個數字要一起畫出來—— 少了後者，被切掉的那一族（例如唯一一個擷取失敗的檔）會整族從畫面上消失，而它往往正是 最該看的那一個。 ⑥ **任何上限／截斷都在消費點外顯**：清單的總筆數／頁碼／每頁筆數（分頁）、總覽每組只附 前 N 筆（不是分頁，要逐筆看走清單）、命中窗天數（預設 7 天而不是 30——一次最多彙總 5000 則問答）、單次掃描的記錄數上限（超過就整趟擋下、不靜默只掃前 N 筆）、沒掃到的檔 那張表的列出數與總數（見⑤）、記錄標題只回前 N 個字而原文長度另有一格、三項命中檢查 這一次到底跑了沒有（三態），以及**這一次哪些記錄的哪一項沒有被檢查**（見下）。 **每一個上限的數字都要讀得到、不在畫面上寫死**：前端自己抄一份的那一天，改了上限畫面 照樣印舊的數字，而「掃了一半」與「掃完了」正是靠那一對數字才分得出來。 ⑦ **「這一次沒有做這一項」與「做了、沒問題」必須分得出來**。掃描結果有兩個數字專門 承載這件事，兩者都是**排除的事實**、不是統計花絮： · 沒有欄位槽的記錄＝資料夾匯入的整份文件（欄位對照是逐列匯入才有的東西）。這些記錄 **被排除在標籤缺口與未填基準日之外**——不是「檢查過而且沒有缺口」。少了這個數字， 兩者在畫面上長得一模一樣。 · 只做得了完全相同比對的記錄＝內容長度超過兩兩比對上限的那一批。相似度是兩兩比對， 成本隨字數平方成長，所以超過上限的那一批**只做逐字相同判定**：同一份上傳兩次仍然 抓得到，「幾乎一樣的兩份」這一次沒有比。這是**漏報方向**的偏差，與本頁其他地方的 取捨相反，所以更要寫出來。 兩個數字**常駐**（0 也畫），理由與命中檢查那一格相同：只在非 0 才出現的話，看不到它就 分不出是「這一次沒有被排除」還是「這個版本不報這件事」。 i18n 的兩處刻意分 key（§4-2「語意確實不同、英譯必須區別才分 key」）： · `health.statusOpen`（未處置／Open）與既有的 `agent.stepPending`（待處理／Pending）—— 前者是發現還沒有人處置，後者是管線節點還沒開始跑，英譯本來就不同。 · `health.actionDismiss`（判定為非問題）與 `health.statusDismissed`（已判定為非問題）—— 一個是動作、一個是狀態，繁中已經分得開。 **記錄的可讀身分**：一筆發現的記錄鍵與記錄本身同序等長，逐筆帶得出標題。「保留哪一筆」 「哪一筆是現行版」「補寫在哪一筆」三個選項是使用者據此做出的、**會改資料的決定**——只有 一串文件識別碼雜湊的話，那幾支處置在畫面上沒有辦法用。 渲染走 `components/record-identity`（同一頁五處共用）：**標題永遠帶著「這是哪一種身分」** （逐列匯入的一列／資料夾匯入的整份文件／查無主題的問法，三種東西長得都像標題但意思不同）、 同名時靠檔案與列號分辨、標題欄空白與標題讀不出來分成兩句話講、截斷說得出原文有多長。 處置吃的仍是記錄鍵（畫面上讀的是記錄本身，兩者不得分家），所以「涉及的記錄」那一列在標題 後面仍然列得出文件識別碼。 權限：清單與總覽掛 `data:read`，掃描與五支處置＋還原掛 `data:write`。 切版不做權限過濾（那是 React 應用層的事）：能力不足**不做「不渲染／不可按」**，鈕照樣按得
