{# 四欄的上限與格式是契約欄位（§6），**數字走資料節點、不烤進譯文**（§4-2），而且**那顆數字 自己也是資料、不是字面量**：同一顆上限在這一頁有四個落點（新增區的 `maxlength`、新增區的 可見提示、逐列就地編輯的 `maxlength`、表格下方那份共用提示），逐格寫死＝同一份契約在一頁裡 烤了四份抄本（§3-2「重複資料在頁面資料化」、§6「同一份業務目錄不得各烤一份」）。開成一顆槽 之後它在轉換契約上就是 props：執行期由那份設定上限資料填進來，不必在每一處各寫一次—— 多一份字面量就多一個會靜默過期的地方。 **四欄的值域在這裡宣告**： · 表名稱 64 字、何時查閱 1024 字、補充指示 1024 字，三欄都**不可含 XML/HTML 標籤**—— 這三欄會原文進工具中繼資料＝常駐在每一輪對話的提示詞裡，標籤混進去就是一道注入面。 · 正規化 regex 500 字，而且必須編得起來：**不可含量詞（* + ? {}）、交替至多一個**—— 這兩種寫法會讓比對在長輸入上爆炸性回溯。 **新增區與逐列就地編輯兩處都要掛**（§4）：兩處是同一組守衛，只掛新增區等於那條約束在 編輯路徑上不存在。逐列那四顆吃表格下方那一份共用提示（正典＝ glossary-entries-modal 的 `#glossaryLimitsHint`）。 #} {% set glossaryFieldLimits = { tableName: 64, whenToConsult: 1024, toolPrompt: 1024, normalizeRegex: 500 } %} {# 新增術語表：名稱（必填）＋何時查閱＋工具提示（textarea）＋新增鈕（五態 toast：成功／權限不足／填錯／失敗／到達張數上限）。 **這顆鈕的結果共五條，逐條對回 data-toast**（§3-2 負面斷言要列全部出口）： ① 沒有 data:write（閘門由這顆鈕的 data-capability 宣告，結果本身是**第 2 段 warning**—— GUIDELINE §4：能力不足不做「不渲染／不可按」，照樣按得下去、把那一態列進 data-toast） ② 表名稱空著 ③ 正規化 regex 三種不合法：超長／編不起來／含量詞或兩個以上交替 ④ **驗證分兩處做，這一條最容易整條漏掉**：送出之後還要再過一道檢查，而那一道會把結果 **分流**成兩種——分得出「是使用者填的東西不對」的，原句直接送到眼前（原句指名了撞到 哪個名字、哪一張設定檔還在引用這張表，那是使用者唯一據以行動的資訊，所以不改寫）； 分不出來的一律當成故障 ＋ 關聯編號。三欄的長度、三欄的標籤檢查與 regex 檢查全部落在 前者，使用者自己改得掉 ⇒ 併進 warning 段；故障那一條說得出是伺服器端的事、落在 error 段。 **分流的方向是刻意不對稱的**：把故障講成「你輸入錯了」比反過來危險得多——前者沒有日誌、 沒有告警、沒有關聯編號，使用者被指去改一個沒問題的欄位。 ⑤ **這個租戶的術語表張數到頂**（上限 30 張，在這裡宣告）。配額算在租戶身上。 **它是 warning、不是 error**：使用者刪掉用不到的表就建得起來。 **而且一定要有自己的一段**：併進第 3 段「表名稱不可為空、任一欄超過長度上限……」的話， 第 31 張會讓使用者回頭改名字、改欄位、改 regex——每一項都不是原因，改到底也不會有結果。 **無重名檢查**：建表只跑上面那幾道驗證，沒有任何唯一鍵分支，故不列「名稱已存在」 （列一個不可能發生的結果與只演成功一樣是說謊，§5）。 ⚠️ **第 5 段刻意不帶「現在幾張／上限幾張」**：`data-toast` 是屬性型譯文（§4-2 的唯一例外）， 把數字烤進去就要同頁另有一處常駐可見的節點承載它——那一處就是下方「術語表清單」標題列的 計數（`已 N / 30 張`）。段落本身只講「為什麼有上限」與「下一步」，不改寫擋下來的那一句 （同一顆鈕在不同錯誤下不該講兩種語氣）。 #}
