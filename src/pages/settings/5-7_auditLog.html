{# 查詢區：操作類型篩選（`ui/search-select`，送出去是**逐字精確比對**、不做模糊）；此靜態頁列 代表性選項，React 端列完整操作類型清單。正式環境的 tbody 是 React 在執行期依查詢結果渲染的， 切版這一側以 set＋for 資料化示範 3 筆。 **本頁的七顆篩選控制項全部是「值載體」**（§5 組合矩陣②：值交給 React 讀去送查詢參數， 成敗由查詢鈕演，click 委派也抓不到 select 的 change）——不是只有掛了 hook 的那一顆。 七顆是：`#auditActionSelect`（操作類型）／`#auditUserSelect`（使用者）／`#auditGroupSelect` （群組）／`#auditStartDateInput`（開始時間）／`#auditEndDateInput`（結束時間）／ `#auditTenantInput`（指定租戶）／`#auditScopeAllInput`（全部租戶）。 **React 綁定記號擇一即可，class hook 或 id 契約都算**（§5 矩陣那一條，正典是 2-2-1 以 `#knowledgeConfigSelect`／`#llmModelSelect` 綁定的那兩顆 select）：這幾顆各自有唯一 id， 其中 `#auditTenantInput` 另外掛了 `.js-audit-tenant`——那**不是本頁的規矩**，是既成事實： 那顆 hook 已經有人照它定址，而 §5「hook 名一經訂下就凍結，不因命名風格改名」 ⇒ 不為了七顆一致而補其餘六顆，也不為了風格一致而拿掉它。 ⚠️ 所以這一段的說明**要寫成七顆的通則**：只替掛了 hook 的那一顆寫「值載體 → 只掛 hook class」， 會讓同一頁對同一種控制項出現兩套說法——其餘六顆一顆 hook 都沒有，卻同樣是值載體。 **本頁那道閘不是單純的「有沒有 `audit` 能力」**： 它是一道 **OR** 閘——**平台稽核員**（平台角色 ∈ {auditor, admin}） **或**（使用期有效 ∧ 租戶開通 audit ∧（租戶管理者 ∨ 持有 audit 能力））。 為什麼不能只看能力：純能力閘只對平台系統管理員放行， 於是平台**稽核員**會被當成一般租戶使用者，而稽核員典型上不是任何租戶的管理者、 能力集是空的，結果是他連自己租戶的稽核都打不開。 四軸擺不下 OR，故本頁的分法是：**最寬的那一條掛區塊**（下面**兩個**欄位的 `data-platform-role="auditor"` ——租戶與「全部租戶」，數一數就是兩個，寫成別的數字就對不上 markup）， **最窄的那一條掛控制項**（查詢鈕的 `data-capability="audit"`，＝租戶那一半）。 `data-capability="audit"` 這個字面，套在純能力閘與上面那道 OR 閘上長得一模一樣， 所以 OR 的兩邊要逐字寫在這裡——照字面看不出這一頁走的是哪一種。 租戶（指定租戶／「全部租戶」開關）那兩個篩選欄位要**平台角色**才動得了， 而那是**稽核員也有的**：判斷這兩件事看的是「平台角色 ∈ {auditor, admin}」， 不是「是不是平台系統管理員」——後者會把唯讀稽核員一起排除掉。 故上列這幾欄一律掛 data-platform-role="auditor"（§5 兩級可見性）， **它們都是值控制項（switch／input），不是動作鈕**，所以套的是 §5 兩級可見性的另一半： 低於該級時**照渲染但 disabled**，不是不渲染——狀態要看得見才稽核得到。 ⚠️ 兩個常見的寫反：說成「`data-platform-role` 決定是否渲染」，照著做出來的是這條規則的反面 （正確的寫法在 5-6-1／5-6-3）；以及把那兩欄說成「要平台角色才**看得到**」——它們一律看得到， 只是**動不了**，所以措辭一律用「才動得了」。 此靜態頁展示的是有平台角色、可操作時的完整版面。 #}
{# **兩列的分法**：第一列＝「誰做了什麼」（操作類型／使用者／群組），第二列＝「什麼時候、 哪個租戶」。不是版面偏好——「清除」要把七顆一起帶回預設，而它們的預設態不一樣 （六顆清空、`#auditScopeAllInput` 回到「開」），分組讓那條規則在 markup 上讀得出來。 **前三顆是 `ui/search-select`（`.searchSelect`）而不是原生 `singleSelect`**：操作類型 有 ~120 個選項（React 端列完整清單，此靜態頁列代表性選項），原生 select 只能一顆一顆 捲——使用者知道自己要找「資料集」那一族，卻沒有任何方法問出來。使用者／群組兩顆在 成員多的租戶上是同一個問題，故三顆同款。 **`#auditUserSelect`／`#auditGroupSelect` 的選項是執行期填進來的** （取名冊那一趟過的是**與稽核列同一道閘**，不是「限租戶管理者」——否則有 `audit` 能力的一般成員與平台稽核員拿到的會是空下拉，而空下拉與「這個租戶沒有群組」 在畫面上一模一樣）。 此靜態頁列示範選項。 #}
{# **無效格由 markup 表達**（§3-2）：「全部租戶」開著時名冊回的是空的 （跨全部租戶時這一欄沒有值域可言），故這一欄與租戶欄同一態——本頁示範的是 開關 ON 的狀態，所以渲染成 `disabled`：照渲染但改不動，狀態要看得見。 #} 「全部租戶」開啟時本欄不生效；留空＝不限使用者。清單是本租戶的成員。
{# hint 講的是**這個篩選到底在篩什麼**（§3-2 值域寫在填之前）：稽核列沒有存 操作當下的群組歸屬，篩選是拿「目前的成員名單」去比對操作者。換過群組的人， 他過去的操作會跟著他現在的群組跑。那是這個篩選的語意、不是缺陷——但沒有這句話 的話，看的人會把一份正確的結果讀成錯的。 另一半：**「全部租戶」開著時帶群組會被直接擋下**（群組是租戶內的概念， 跨租戶必然指不到東西），所以那時這一欄是死的。 #} 依成員目前的群組歸屬篩選——不是操作當下的歸屬，換過群組的人，他過去的操作會跟著現在的群組。「全部租戶」開啟時本欄不生效。
{# 起訖欄是日期選擇器的掛點（`.start-date`／`.end-date`），切版不引 vendor、 只保留 class 與 `.time` 的日曆圖示變體； 日期選擇交由 React 端的套件實作（同 components/data-time-filter 的做法）。 **本頁刻意不用 components/data-time-filter**：那一支把「時間區間最長 365 天、 開始時間不得早於 365 天前」烤進它的常駐說明與兩個消費頁的 toast。 稽核查詢**沒有**這兩條界線——調兩年前那一天的紀錄正是 ISO 證跡 存在的理由。借用那個元件會在畫面上宣告一條根本沒有人在執行的限制。 #}
{# 這一欄是「指定要查哪一個租戶」的落點（有平台角色的人才查得了別人的租戶）。 §3-2：查詢收得下的每個條件都要有落點——少了它，畫面就只做得到 「全部租戶或自己那一個」，指定單一租戶送不出去。 值載體 → 只掛 hook class（§5 矩陣②）。 #}
{# `.js-audit-tenant` 是**凍結**的 hook（已經有人照它定址，見檔頭）：不改名、 也不因為同頁另外幾顆走 id 契約就把它拿掉。 #} {# **無效格由 markup 表達**（§3-2，不能只寫在 hint 裡）：查詢的優先序是「有平台角色 ＋『全部租戶』開著 ⇒ 完全不加租戶過濾」，關掉之後才輪得到這一欄 ——「全部租戶」開著時這一欄**無條件被短路掉**，那一格是死的。本頁示範的是 開關 ON 的狀態，故這一欄同時渲染成 `disabled`（照渲染但改不動，狀態要看得見）。 hint 要講的是**誰蓋過誰**（開關蓋過這一欄），不是「什麼時候看誰」：後者在兩個 方向上都讀得通，於是它寫反了也一樣讀得通——「留空＝依開關決定」就是那種 看起來沒問題、實際與真正的優先序相反的句子。 區間本身要讀得到（§4）：`min="1"` 是切版自己加的（送出去那一側對這個值沒有上下界）， 更要說得出來。 #} 「全部租戶」開啟時本欄不生效，填了也會被忽略；關閉後才填得動。填租戶 id（≥ 1 的正整數），留空＝只看自己租戶
{# 起訖兩欄共用的常駐說明（§3-2 值域寫在填之前）：兩端都含、留空＝不限， 且**沒有**任何天數上限——見上面起始欄那一段為什麼不借用 components/data-time-filter。 #}

起訖兩端都包含在內；留空＝不限。稽核軌跡不設查詢天數上限，查得到多久以前的紀錄取決於保存了多久。

{# 示範 3 筆已載入狀態；操作者/對象/詳情/IP 為假資料（§3-2，不翻）。 ⚠️ **每一列都要逐欄對回「那一顆 action 真的寫得出來的形狀」**（§6：示範資料的每一欄 都要對得回一個真的存在的欄位）。這張表上有三組欄位特別容易編出產不出來的組合： ① **租戶欄與操作者欄同生同滅**：這兩欄都取自「做這件事的那個帳號」，查不到帳號時兩欄 一起是空的。所以操作者是「—」（本表的語意逐字是「登入失敗查無操作者」，見下一段） ⇒ 租戶欄必然也是「—」，不可以配一個租戶號碼。 （帳號存在但被停用的那一條路不同：`detail` 會多一顆 `reason: "inactive"`，而且操作者查得到， 那是另一種列。）本表因此只剩兩個租戶，跨租戶檢視照樣示範得到。 ② **`login.failed` 的對象欄一定有值**：那一支 action **無條件**帶對象——型別是 `login`、 識別碼是**正規化後的 email**，而登入節流正是靠這一欄計數（拿使用者 id 當對象的話， 不存在的 email 永遠累積不到計數）。識別碼是 email 不是整數 id， 所以這一格畫不出「#數字」；它與 `detail` 裡的 email 重複，本來就是這樣寫的。 ③ **`ask` 那一列反過來：對象欄一定是「—」、`detail` 一定有 `query`**。那一支 action 只帶 `detail`（`query` 與 `tag`），**完全沒有對象**——編一顆 `chat_log #…` 出來就是 憑空造了一個不存在的欄位； 而少了 `query`，這條路徑上最關鍵的欄位在切版裡等於不存在。 **`detail` 的遮蔽是兩道判準不是一道**：載著提問原文的那一族鍵不看長度一律遮， 其餘鍵走 allowlist ＋ 長度上限，沒登記又過長的一樣被換掉—— 遮蔽面遠大於「一顆 query」。⚠️ 這一格另有一態：沒有 `history` 能力的稽核者看到的是 一句「內容已隱藏（N 字）」，那句話是連著資料一起送過來的、不是本專案的譯文。 **「操作類型」不是假資料，是同一份封閉目錄**（稽核列真的寫得出來的那組 action 詞彙）： 上面的篩選下拉逐顆掛了 `audit.act*` 的 key，**列裡就不可以把同一組詞當純文字再烤一份繁中** ——那會讓英文模式下同一頁同時出現 "Create dataset" 的下拉與「建立資料集」的表格（§4-2／§6： 一份目錄只能有一份正本）。故每一列帶三件事：`action`＝那顆詞彙的字面（＝下拉的 `
