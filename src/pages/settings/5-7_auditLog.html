{# 查詢區：操作類型篩選（`ui/search-select`，對照後端 GET /audit?action= 精確比對）；此靜態頁列 代表性選項，React 端列完整操作類型清單。真實頁 tbody 由 React 依查詢結果渲染，此處以 set+for 資料化示範 3 筆。 **本頁的七顆篩選控制項全部是「值載體」**（§5 組合矩陣②：值交給 React 讀去送查詢參數， 成敗看後端，click 委派也抓不到 select 的 change）——不是只有掛了 hook 的那一顆。 七顆是：`#auditActionSelect`（action）／`#auditUserSelect`（user_id）／`#auditGroupSelect` （group_id）／`#auditStartDateInput`（start）／`#auditEndDateInput`（end）／ `#auditTenantInput`（tenant_id）／`#auditScopeAllInput`（scope=all）。 **React 綁定記號擇一即可，class hook 或 id 契約都算**（§5 矩陣那一條，正典是 2-2-1 以 `#knowledgeConfigSelect`／`#llmModelSelect` 綁定的那兩顆 select）：這幾顆各自有唯一 id， 其中 `#auditTenantInput` 另外掛了 `.js-audit-tenant`——那**不是本頁的規矩**，是既成事實： saas 端已經引用它（`apps/web/app/(app)/audit/page.tsx` 的 `className="form-control js-audit-tenant"`）， §5「hook 一經 saas 端引用即凍結，改名＝跨 repo 遷移」⇒ 不為了七顆一致而補其餘六顆，也不為了風格一致而拿掉它。 （原本這裡只替那一顆寫了「值載體 → 只掛 hook class」的理由，讀起來像本頁對值載體的通則， 而其餘幾顆一顆 hook 都沒有——同一頁對同一種控制項寫了兩套說法。） **本頁那道閘是 `require_audit_access`（product `app/authz.py`），不是 `require_capability("audit")`**： 它是一道 **OR** 閘——`is_platform_auditor` **或**（訂閱 active ∧ 租戶開通 audit ∧（租戶管理者 ∨ audit token））。 上游 docstring 逐字說明為什麼不能直接用 `require_capability`：那支只對 `is_platform_admin` bypass， 於是 `platform_role='auditor'` 會被當成一般租戶使用者，而稽核員典型上不是任何租戶的 admin、 能力 token 為空集，結果是他連自己租戶的稽核都打不開。 四軸擺不下 OR，故本頁的分法是：**最寬的那一條掛區塊**（下面**兩個**欄位的 `data-platform-role="auditor"` ——租戶與「全部租戶」，數一數就是兩個；先前這裡寫「三個」，而本頁從來只有那兩顆掛著它）， **最窄的那一條掛控制項**（查詢鈕的 `data-capability="audit"`，＝租戶那一半）。 `data-capability="audit"` 這個字面對 `require_capability("audit")` 與 `require_audit_access` 長得一模一樣， 所以 dependency 的名字要寫在這裡——照字面看不出指錯了哪一支。 租戶（指定 tenant_id／全部租戶 switch 送 scope=all）那兩個篩選欄位要**平台角色**才動得了， 而那是 auditor 亦有的能力：product app/routers/audit.py 的 list_audit 以 is_platform_auditor （platform_role ∈ {auditor, admin}）判斷 scope=all／tenant_id，該檔自註「用 is_platform_admin 判斷會把唯讀稽核員一起排除掉」。故上列這幾欄一律掛 data-platform-role="auditor"（§5 兩級可見性）， **它們都是值控制項（switch／input），不是動作鈕**，所以套的是 §5 兩級可見性的另一半： 低於該級時**照渲染但 disabled**，不是不渲染——狀態要看得見才稽核得到。 （原本這裡寫「決定是否渲染」，照著做會做出規則的反面；5-6-1／5-6-3 兩頁寫的才是對的。 上面那句原本也寫成「才**看得到**」——與這一句自相矛盾，一併改成「才動得了」。） 此靜態頁展示的是有平台角色、可操作時的完整版面。 #}
{# **兩列的分法**：第一列＝「誰做了什麼」（操作類型／使用者／群組），第二列＝「什麼時候、 哪個租戶」。不是版面偏好——「清除」要把七顆一起帶回預設，而它們的預設態不一樣 （六顆清空、`#auditScopeAllInput` 回到「開」），分組讓那條規則在 markup 上讀得出來。 **前三顆是 `ui/search-select`（`.searchSelect`）而不是原生 `singleSelect`**：操作類型 有 ~120 個選項（React 端列完整清單，此靜態頁列代表性選項），原生 select 只能一顆一顆 捲——使用者知道自己要找「資料集」那一族，卻沒有任何方法問出來。使用者／群組兩顆在 成員多的租戶上是同一個問題，故三顆同款。 **`#auditUserSelect`／`#auditGroupSelect` 的選項是執行期由 `GET /audit/filters` 填的** （product `app/routers/audit.py::audit_filter_options`，閘與稽核列同一道 `require_audit_access`——不是 `require_admin`，否則有 `audit` 能力的一般成員與平台 稽核員拿到的會是空下拉，而空下拉與「這個租戶沒有群組」在畫面上一模一樣）。 此靜態頁列示範選項。 #}
{# **無效格由 markup 表達**（§3-2）：`scope=all` 時 `GET /audit/filters` 回空名冊 （跨全部租戶時這一欄沒有值域可言），故這一欄與租戶欄同一態——本頁示範的是 開關 ON 的狀態，所以渲染成 `disabled`：照渲染但改不動，狀態要看得見。 #} 「全部租戶」開啟時本欄不生效；留空＝不限使用者。清單是本租戶的成員。
{# hint 講的是**這個篩選到底在篩什麼**（§3-2 值域寫在填之前）：`AuditLog` 沒有存 操作當下的群組歸屬，篩選是拿「目前的成員名單」去比對 `user_id`。換過群組的人， 他過去的操作會跟著他現在的群組跑。那是這個篩選的語意、不是缺陷——但沒有這句話 的話，看的人會把一份正確的結果讀成錯的。 上游對應：product `list_audit` 的 `user_id IN (SELECT user_id FROM user_groups …)`， 且 `scope=all` 時直接回 400（群組是租戶內的概念，跨租戶必然指不到東西）。 #} 依成員目前的群組歸屬篩選——不是操作當下的歸屬，換過群組的人，他過去的操作會跟著現在的群組。「全部租戶」開啟時本欄不生效。

{# 示範 3 筆已載入狀態；操作者/對象/詳情/IP 為假資料（§3-2，不翻）。 ⚠️ **每一列都是逐欄對回 `list_audit` 那一顆 action 真的寫得出來的形狀**（§6：示範資料的每一欄都要 對得回正本回應的一個欄位），round45 逐筆修過三處： ① `login.failed` 那一列原本 `tenantId: 31` 配操作者「—」。product `auth.py` 的兩處 `record_audit` 寫的是同一個三元式的兩半（`tenant_id=user.tenant_id if user else None`、 `user_id=user.id if user else None`）⇒ 兩欄同生同滅。而「—」在本表的語意逐字是 「登入失敗查無操作者」（見下一段），也就是 `user is None` 那一條路 ⇒ tenant_id 必然也是 None。 （帳號存在但被停用的那一條路 `detail` 會多一顆 `reason: "inactive"`，而且操作者查得到， 那是另一種列。）故租戶欄改畫「—」；本表因此剩兩個租戶，跨租戶檢視照樣示範得到。 ② 同一列的 `target` 原本「—」。那一支 action **無條件**帶 target：`auth.py` 兩處都寫 `target_type=LOGIN_TARGET_TYPE, target_id=email`，而登入節流正是靠這一欄計數 （`app/login_guard.py` 的 `LOGIN_TARGET_TYPE = "login"`，該處註解逐字說明「用 user_id 會讓 不存在的 email 永遠累積不到計數」）。`target_id` 是**正規化後的 email**（不是整數 id）， 所以這一格畫不出「#數字」；它與 `detail` 裡的 email 重複是上游本來就這樣寫。 ③ `ask` 那一列原本編了 `chat_log #4821`。`ask` 的 `record_audit`（product `app/routers/ask.py`） 只帶 `detail={"query": query, "tag": tag}`，**沒有 target_type/target_id** ⇒ 對象欄是「—」。 同一列的 `detail` 也補回 `query`：`app/routers/audit.py` 的 `_project_detail` 分級投影的就是 這一族鍵（`_QUERY_SCOPED_DETAIL_KEYS`，**不抄成員**——上游自己註明「先前這裡只有 `query` 一顆」， 抄一份就是抄一份會過期的舊清單，§3-2），原本那一列沒有 query，等於這條路徑上 最關鍵的欄位在切版裡不存在。**遮蔽是兩道判準不是一道**：那一族鍵不看長度一律遮，其餘鍵走 allowlist（`_VERBATIM_DETAIL_KEYS`）＋長度上限（`_MAX_VERBATIM_DETAIL_CHARS`），未登記又過長者一樣被換掉—— 遮蔽面遠大於「一顆 query」。⚠️ 這一格另有一態：沒有 `history` 能力的稽核者看到的是 `audit.query_hidden`（上游把內容換成字數），那句話由 product 的 i18n 產生、不是本專案的譯文。 **「操作類型」不是假資料，是同一份封閉目錄**（product `record_audit` 寫進去的那組 action 詞彙）： 上面的篩選下拉已經逐顆掛了 `audit.act*` 的 key，列裡卻把同一組詞當成純文字烤了第二份繁中 ——英文模式下同一頁會同時出現 "Create dataset" 的下拉與「建立資料集」的表格（§4-2／§6： 一份目錄只能有一份正本）。故每一列改帶三件事：`action`＝上游字面（＝下拉的 `
