標籤維度把一個實體篩選槽宣告成一個業務維度，再配一組受控詞彙；問答時由意圖分類挑出代碼、組成檢索過濾條件。引擎本身不認得任何業務代碼，它只知道「這一欄等於這個字串」。

{# ── 新增標籤維度 ─────────────────────────────────────────────────────────────── 四道寫入當下就判得出來的限制由 product 擋（`_validate_slot_and_kind`／`_validate_role`／ `_assert_slot_and_role_free`），故送出鈕的 toast 列得出「槽已經有維度了／角色已指派」這一態。 前端不再寫一份界線判斷（那是第二個真相）。 #}
新增標籤維度
{# 值域是 12 個，不是這一頁湊得出來的四個：`TAG_SLOT_KEYS = tag_dimension_slots(SLOTS)` ＝角色為 `custom_field_mapping` 的槽（tags.py:50-63 → field_schema.py:37-48）， 也就是 note1..note10 ＋ date2/date3。本頁自己的 hint 就是這樣寫的，示範資料裡 還有一筆掛在 note3 的維度——只列四個等於 note3..note10 永遠建不出維度。 **不硬編**：`GET /settings/tag-dimension-contract` 的 `slots` 是這份值域的單一真相 （tag_dimension_contract.py:40-42 明寫「一個都不能留在前端硬編」）， 切版以 set 陣列表達那份回應（§6），React 端改讀端點。 第一顆是空值「請選擇」：開頁就宣告已挑好 note1，而 note1 在示範資料裡已被佔用 ⇒ 第一次送出必撞「這個槽已經有維度了」（§4「還沒挑」沒有任何一顆 option 承載得住）。 #} {% set tagSlotKeys = ["note1", "note2", "note3", "note4", "note5", "note6", "note7", "note8", "note9", "note10", "date2", "date3"] %}

只有 product 宣告給檢索引擎當自訂篩選欄位的那些槽（note1–note10、date2、date3）承載得了維度；內建槽的 DSL 引用會被上游拒絕。一個槽只能有一個維度，一個角色也只能指派給一個維度。

單值＝三選一；多值＝可複選；日期＝做大小比較。日期槽（date2／date3）只能是日期型別，其餘槽不能是日期型別——配錯的組合每一次檢索都會被上游擋下。

角色是給引擎內建機制認的：valid_until／as_of 只能掛在日期維度、fact_topic／superseded_by 只能掛在單值維度。配錯不會報錯，只會讓該機制完全跳過這個維度——設定頁看起來一切正常，而它從頭到尾沒有作用過。

{# ④ 日期上下界：講在**填之前**。這一段對 kind=date 常駐顯示（React 依所選型別擇一渲染）。 **兩個日期是資料不是譯文**（§3-2）：它們在契約裡有欄位——`GET /settings/tag-dimension-contract` 的 `filterable_date_range.min_date`／`max_date`（tag_dimension_contract.py:115-116）， 而那支端點的檔頭點名的失敗樣態正是「區間改了而畫面照舊寫著舊日期」。 故拆成資料槽 ＋ 前中後三段可翻的文字（同 414eecc 對 5-2 三個上下界做過的修正）。 #} {% set filterableDateMin = "1677-09-21" %} {% set filterableDateMax = "2262-04-11" %}

日期維度的值必須落在 {{ filterableDateMin }} 到 {{ filterableDateMax }} 之間：檢索引擎把日期存成 64 位元奈秒數，超出去會溢位成另一端的時間。出界的值存得進去、精確比對也找得到，但任何用到日期範圍的過濾都會漏掉那份資料，查詢時它只是不見了、不會有錯誤訊息。若本來就是想表示「永遠有效」，請把該格留白，系統會自己補上不會過期的值。

{# ── 檢索過濾旋鈕（每套設定檔各一份）─────────────────────────────────────────── product `RetrievalProfile.retrieval_filter_mode` 預設 `off`、`recent_window_days` 預設 7。 開啟走 `PUT /retrieval/profiles/{no}/tag-filter`，它會**先量再開**：量不到零筆未標註就 400， 旋鈕維持 off、證明快照不變。故開關這顆的 toast 一定要有「覆蓋率不足」那一段 warning ——只演成功等於把整道閘門演掉了。 #}
標籤檢索過濾

開啟之後，問答會先判斷這一題屬於哪些業務維度，再把判斷結果編成檢索過濾條件送給引擎。判不準時整組條件一起丟棄（連時間窗一起），不會退成一條寬鬆的條件。

{# ② 覆蓋率不足＝大規模誤殺的警語，就放在開開關的地方。兩態各自完整敘述後果，未生效的那句掛 .hidden（React 依「還有沒有維度拿不出零筆未標註的證明」擇一渲染）。 #}

目前還有維度拿不出「零筆未標註」的證明。在這個狀態下開啟過濾，那些沒標註的文件會被過濾條件靜默排除——agent 模式沒有無結果放寬階梯，被濾掉就是真的消失，而使用者只會體驗成「有些資料查不到」。這正是這顆旋鈕預設關閉的理由。

目前每一個「未標註表達不出來」的維度都量到零筆未標註，可以開啟。之後若又匯入一批該欄留白的文件，覆蓋率會掉下去而旋鈕還開著——那些文件會被靜默濾掉，所以補完資料請回來重新量測一次。

{# ③ 時間窗不能獨立於維度存在：講清楚它跟著意圖判定走、判不準就一起歸零，以及為什麼。 #}

「最新資料時間窗」不是一顆可以單獨生效的開關：它只在意圖分類判定這一題在問最新資料時才會出現，而判不準時整組條件連同時間窗一起丟棄。理由是時間窗是唯一沒有「未標註」分支的述詞——留著它就會連沒有發布日的文件一起濾掉。
